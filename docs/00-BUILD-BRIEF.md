A multi-tenant SaaS for dental practices, modelled on **Sterily.fr** and its French competitors (e-stericode, SterileConnect), extended with the stock/purchasing module those tools lack.

**The problem it replaces:** practices currently log sterilization in paper notebooks and Excel sheets. When a health authority inspects (ARS in France), they must be able to prove, for a given patient and a given procedure, that the instruments used came out of a *compliant, released* sterilization cycle — with operator, sterilizer, cycle number, date/time, load composition and use-by date.

**The core loop the product must make effortless:**

```
receive stock (batch + expiry)
   → prepare a load and run a sterilization cycle on an autoclave
   → record the cycle result and the control tests
   → an authorized person RELEASES the cycle (compliant / rejected)
   → the system prints one unique 2D-coded label per pouch
   → at the chair, the label is scanned before use
   → the scan links pouch → cycle → device → practitioner → procedure → (pseudonymized) patient
   → one click produces the complete inspection-ready evidence dossier (PDF)
```

**Feature parity targets taken from Sterily:** real-time cycle and test logging; a compliant control-test logbook (vacuum/Bowie-Dick/Helix) with reminder alerts so a mandatory test is never missed; unique QR-coded label per pouch; scan-at-use writing straight into the patient record; complete searchable history; one-click inspection dossier; 15–30 day self-serve trial.

**Deliberately out of MVP scope** (do not build, do not scaffold): advanced SaaS billing, marketplace, complex multi-site, predictive analytics, universal autoclave compatibility, heavy per-tenant customization, more than one real partner connector.

## 4. ARCHITECTURE

### 4.1 Repository layout

```
/app
  /Domain/<Context>/          # Models, Actions, Data, Events, Policies, StateMachines
      Tenancy/ Identity/ Catalog/ Purchasing/ Inventory/
      Equipment/ Sterilization/ Labeling/ Traceability/ Reporting/ Compliance/ AI/
  /Http/Controllers/Web/      # Inertia controllers
  /Http/Controllers/Api/V1/   # Mobile REST controllers
  /Support/                   # Tenancy scopes, idempotency, audit, exports
/resources/js/                # React + Inertia (pages/, components/, layouts/, lib/)
/database/migrations|factories|seeders
/docs/                        # openapi.yaml, erd.md, adr/, runbook.md, open-questions.md
/docker/                      # Dockerfile, compose files, entrypoints, nginx-less FrankenPHP config
/tests/Unit|Feature|Api|Contract|E2E
```

Business logic lives in single-purpose **Action** classes (`ReleaseCycleAction`, `RecordStockMovementAction`). Controllers validate, authorize, delegate, respond. No business logic in controllers, models or React.

### 4.2 Multi-tenancy — the most important design decision

- **Single database, shared schema.** Every tenant-owned table carries a non-null `tenant_id` (UUID) with a foreign key and an index; every unique constraint is scoped `(tenant_id, …)`.
- `spatie/laravel-multitenancy` resolves the current tenant (subdomain in web, token-bound tenant in API) and binds it to the container; it also makes queues, cache keys and mail tenant-aware.
- A `BelongsToTenant` trait adds a global scope (filter on read) **and** auto-fills `tenant_id` on create.
- **PostgreSQL Row-Level Security is enabled on every tenant table** with a policy on `current_setting('app.tenant_id')`, set per connection in a middleware/Octane hook. The application scope is line one; RLS means that even a forgotten scope or a raw query cannot leak across tenants. This is what makes REC-01 and risk R-06 genuinely closed rather than hopefully closed.
- The tenant is **never** taken from a request parameter. It comes from the authenticated session/token only. Any route that accepts a tenant identifier from the client is a bug.
- `spatie/laravel-permission` runs in **teams mode** with `tenant_id` as the team key, so a user's roles are per-practice.

### 4.3 API conventions (freeze these in S0 — they block the mobile developer)

- Base path `/api/v1`. Versioned, additive-only within a major version.
- JSON only. `snake_case` keys. All timestamps ISO-8601 UTC with offset. All IDs are UUIDv7.
- **Errors — one shape, always:**
  ```json
  { "error": { "code": "CYCLE_NOT_RELEASED", "message": "Human readable, localizable.",
               "details": { "field": ["…"] }, "request_id": "01J…" } }
  ```
  Stable machine `code` per business rule (the mobile app branches on `code`, never on `message`).
- HTTP: 200/201, 204, 400, 401, 403, 404, 409 (state conflict), 410 (recalled/revoked), 422 (validation), 429, 5xx.
- **Idempotency is mandatory** on every state-changing endpoint: client sends `Idempotency-Key: <uuid>`; the server stores key + request hash + response in Redis for 24 h and replays the stored response on repeat. This is what closes REC-02 and risk R-08 — do not rely on the client behaving.
- Cursor pagination (`?cursor=&limit=`), `Retry-After` on 429, `ETag`/`If-None-Match` on read-heavy resources.
- OpenAPI 3.1 generated by Scramble, committed to `docs/openapi.yaml`, published with mock examples, and covered by **contract tests** so it can never silently drift from the code (risk R-02).

## 5. DOMAIN MODEL

`tenants` (name, slug, plan, trial_ends_at, status) · `sites` · `rooms` · `storage_locations` · `users` · `tenant_user` (+ status, invited_at, disabled_at) · `invitations` · `roles`/`permissions`/pivots (spatie) · `personal_access_tokens` · `audit_events`

**Catalogue & purchasing**

**Inventory**
`batches` (product_id, batch_number, expiry_date, supplier_id, received_at, status) · `stock_movements` (**append-only ledger**: type = receipt|issue|transfer|adjustment|count, qty signed, batch_id, from/to location, reason, actor, idempotency_key, occurred_at) · `stock_levels` (materialized projection, rebuildable from the ledger) · `inventory_counts` + lines · `alerts` (type = low_stock|near_expiry|expired|failed_cycle|missing_test, severity, state, resolved_at)

**Equipment & sterilization**
`devices` (autoclaves, sealers, washers: brand, model, **serial_number unique per tenant**, site, commissioned_at, next_maintenance_at) · `device_programs` (name, type: prion/B/S/N, temperature, duration) · `maintenance_records` · `sterilization_cycles` (device_id, program_id, **cycle_number unique per (tenant, device, year)**, started_at, ended_at, operator_id, status, result, ticket_media, notes) · `cycle_loads` / `load_items` (what physically went in: instrument set, product/batch, quantity, packaging type) · `control_tests` (type = vacuum|bowie_dick|helix|biological, cycle_id nullable, performed_at, operator, result, attachment) · `cycle_releases` (cycle_id, decision = compliant|rejected, released_by, released_at, reason, **immutable**)

**Labels & traceability**
`labels` (**uuid public code**, cycle_id, load_item_id, sequence_in_cycle, printed_at, expiry_date/DLU, status = active|used|expired|recalled|voided, qr_payload, datamatrix_payload) · `label_prints` (label_id, printed_by, printed_at, reason, is_reprint, print_counter) · `patients` (**pseudonymized**: external_ref, initials or code, no free-text identity in MVP) · `procedures` (patient_id, practitioner_id, performed_at, act_code) · `label_usages` (label_id, procedure_id, scanned_by, scanned_at, device/site context) · `non_conformities` (subject type/id, kind = recall|quarantine|correction, reason, opened_by, resolved_by, resolution) — corrections are **new rows, never updates**

### 5.1 State machines — implement explicitly, reject invalid transitions at the domain layer

```
purchase_order : draft → ordered → partially_received → received → closed | cancelled
cycle          : draft → running → completed → (awaiting_release) → released | rejected
                 rejected is terminal; released is terminal; nothing edits a terminal cycle
label          : created → printed → used
                              ↘ expired (by DLU)  ↘ recalled  ↘ voided (reprint supersede)
```

### 5.2 Invariants — enforce in the database *and* in code, and test each one

1. Stock quantity is **derived from `stock_movements`**. No endpoint may set a quantity directly. `stock_levels` is a projection that must be rebuildable by replay.
2. **No label may be generated for a cycle that is not `released` with decision `compliant`.** (REC-03)
3. A `cycle_release` row, once written, is immutable. A mistake is corrected by a `non_conformity` + recall, never by an UPDATE.
4. A reprint requires a `reason`, increments `print_counter`, writes a `label_prints` row and voids nothing silently. (REC-05)
5. Scanning a label whose status is `recalled` or `expired` returns **410** with a blocking code and writes an audit event — the mobile app cannot proceed. (REC-04)
6. Disabling a user never rewrites history: past evidence keeps the actor's identity as it was. Users are soft-disabled, never hard-deleted. (REC-06)
7. Every mutation carrying an `Idempotency-Key` is applied at most once. (REC-02)
8. Deletion is soft everywhere; evidence tables (`cycles`, `releases`, `labels`, `usages`, `movements`, `audit_events`) have **no delete route at all**.

### 5.3 Label content — what must be printed

Each pouch gets one unique label. Human-readable zone plus a 2D code (QR **and** DataMatrix supported; the practice picks one in settings):

`sterilizer identifier · cycle/load number · sterilization date and time · use-by date (DLU) · operator · label sequence in cycle · practice/site`

The 2D payload is a short opaque URL/URN containing only the label UUID (`https://steriqore.<tld>/l/<uuid>` or `urn:steriqore:label:<uuid>`) — **never patient data, never a signed secret in the code**. Resolution happens server-side via the scan endpoint.

The DLU is computed from a per-tenant configurable rule table (packaging type × storage conditions), defaulted from the EN 868 family, and stored on the label at print time so a later rule change never rewrites past evidence. Mark the default values `// DECISION NEEDED:` for Salim's dental expert to confirm.

## 6. CROSS-CUTTING REQUIREMENTS

**Audit (`audit_events`)** — actor_id, actor_label_snapshot, tenant_id, site_id, action, subject_type, subject_id, old_values, new_values, reason, ip, user_agent, request_id, occurred_at. Append-only: no UPDATE or DELETE route, and a PostgreSQL trigger that raises on UPDATE/DELETE. Everything sensitive is logged: auth events, permission changes, releases, reprints, recalls, adjustments, exports.

**Security** — server-side authorization on every route via Policies (never a client-side check alone); IDOR test suite that walks every resource as a foreign tenant and expects 403/404; rate limiting per user + per tenant + per IP; strict validation on every input; upload allow-list by MIME + size + re-encoding of images; no secrets in code; OWASP Top 10 pass; security headers + CSP; token revocation and expiry tested.

**Reliability** — every multi-write operation is a database transaction with the right locking (`SELECT … FOR UPDATE` on batch/stock rows); idempotency keys on all mutations; queued jobs are idempotent and retried with backoff; a partner/external API outage must never break the core product (circuit breaker + fallback to manual entry). (REC-07)

**Performance** — common screens < 2 s; evidence search returns complete results **< 2 s at pilot volume** (REC-09) — index for it deliberately and use a `tsvector` GIN index for text search; all lists paginated; N+1 forbidden (assert with a query-count test on the heavy screens).

**Emails via Resend** — invitation, password reset, alert digest (low stock, near expiry, failed cycle, missing control test), weekly evidence summary. All queued, all with a React-Email-like clean template, all logged, all with a tenant-level unsubscribe for digests.

**Privacy** — patient data is minimized to a pseudonymous reference in the MVP; demo and pilot datasets are fully synthetic; **no real patient data may touch this system before the GDPR/HDS decision is written down** (that is Salim's S5 task and it is a hard gate). Data-portability export (§ S6-ANA-03) must return the full tenant dataset plus attachments in a readable archive.

## 7. THE AI LAYER — OPTIONAL, FLAGGED, OUTSIDE THE EVIDENCE PATH

The project spec explicitly defers AI to post-MVP. So build it as a **thin, removable assist layer**, behind `STERIQORE_FEATURE_AI=false` by default, using the **Laravel AI SDK with the OpenAI provider** so the provider can be swapped without touching call sites.

Permitted use cases (all of them *suggest*, a human *confirms*, and the write goes through the same validated Action as manual entry):

1. **Autoclave ticket / cycle report extraction** — the operator photographs the printer ticket; a vision call proposes cycle number, program, temperature, duration, result; the operator confirms or corrects before anything is saved.
2. **Delivery-note extraction** — proposes product lines, batch numbers and expiry dates on receipt; same confirm-before-write rule.
3. **Natural-language search over traceability** — translates "cycles rejected on the Melag in September" into a structured, tenant-scoped, permission-checked query. **The model never receives raw data and never builds SQL** — it emits a constrained filter DTO that your existing query layer executes.
4. **Alert triage / weekly summary** — plain-language digest of anomalies, with links back to the real records.

Non-negotiable AI rules:

- No AI output is ever stored as evidence. AI-proposed values are marked `source=ai_suggested` until a human confirms, and the confirmation is audited with the human's identity.
- No patient identifier and no free-text identity ever leaves the system in a prompt.
- Every call has a timeout, a cost/token cap, a per-tenant rate limit, and a fallback: **if AI is unavailable, every journey still works manually.** AI never appears in an acceptance scenario.
- Log prompt/response metadata (not raw payloads) for audit; store nothing from the provider you would not want in an inspection.
