# Coverage matrix — routes, policies, permissions, nav

Generated by direct inspection of the running route table (`php artisan route:list --json`),
every `App\Policies\*` class, `SeedTenantRolesAction` (the seeder that grants permissions to
roles), `resources/js/config/navigation.ts`, `docs/openapi.yaml`, and every `Inertia::render()`
call site — not from memory or from `docs/ui-backlog.md`. Two small scripts (route↔policy↔
permission joiner, and a route/OpenAPI/page differ) did the cross-referencing; every finding
below was independently re-checked by reading the actual source file it concerns.

This is PHASE 1 of the platform audit only. No code was changed to produce this document.

---

## Summary

- **261** total registered routes; **97** are this app's own web routes and **88** are this
  app's own `/api/v1` routes once framework/vendor routes (Fortify, Sanctum, Horizon, passkeys,
  storage, `.well-known`, Scramble's own docs UI) are excluded. The remaining 6 API routes are
  invokable single-action auth/bootstrap controllers (login, logout, logout-everywhere, me,
  register-tenant, accept-invitation) — public or "authenticated, no specific permission" by
  design, listed separately below.
- **22** Policy classes, all registered via explicit `Gate::policy()` calls in
  `AppServiceProvider` (this app does not rely on Laravel's default naming-convention
  auto-discovery, since models live under `App\Domain\*\Models`, not `App\Models`).
- **33** permissions defined in `SeedTenantRolesAction`. Every single one is checked by at
  least one route, and every permission checked by a route is granted to at least one role —
  **zero dead permissions, zero always-403 routes.**
- **94/94** API routes exactly match `docs/openapi.yaml` — verified as an exact set diff on
  normalized `METHOD /path` pairs. Zero missing, zero extra.
- **29** unique Inertia page components rendered; all 29 exist on disk, and every page on disk
  used by a controller is reachable via a real route. Zero orphans either direction.
- Nav item → route → permission checked three-way, for all 19 top-level nav entries: **100%
  match** between the permission the nav hides an item behind and the permission the
  corresponding route's Policy actually enforces server-side.

**Total findings: 2 real (both minor/cosmetic), 3 verified non-issues worth recording, 1
stale docblock.** No IDOR-class or missing-authorization defects found in this pass.

## Findings (the mismatches — read this section, not just the tables)

### 1. Two Policy abilities are declared but never invoked by any route (dead code)
- `App\Policies\AuditEventPolicy::view($user, AuditEvent $auditEvent)` — there is no
  `audit-events/{auditEvent}` or `audit-log/{auditEvent}` show route anywhere (web or API),
  only `index`/`viewAny`. Confirmed via `grep` across the full route table and controller
  directory: nothing calls `authorize('view', $auditEvent)` or resolves an `AuditEvent` via
  route-model-binding.
- `App\Policies\BatchPolicy::view($user, Batch $batch)` — same shape: no `batches/{batch}`
  show route exists (web or API), only `index`/`viewAny` via `BatchController`/
  `QuarantineController`.
- Severity: cosmetic. Neither is reachable, so neither is a security gap — just dead code
  from an ability that was declared ahead of a "show" screen that was never built (or was
  built differently, e.g. batches are shown inline in a list/drawer rather than a dedicated
  page). Not fixed here per instructions.

### 2. Three routes have no Policy/permission check at all — verified as correct, not bugs
- `dashboard` (`DashboardController@index`) — intentionally open to any authenticated member
  with active practice access; the controller's own docblock says so, and
  `BuildDashboardAction` gates every individual card internally by the same permission its
  target screen requires (verified: `$user->can($card['permission'])` filters the
  attention-cards list, and every onboarding-step/count card is wrapped in its own
  `$user->can('xxx')` check). Not a gap.
- `site/switch` (`SwitchSiteController@store`) — no Policy needed: the allowed `site_id` list
  is built from `Site::query()->pluck('id')`, which is already `TenantScope`-filtered to the
  current tenant, so a foreign or made-up id simply fails Laravel's `Rule::in()` validation.
  Confirmed by reading the file — not a security boundary, a display preference.
- `tenant/switch` (`SwitchTenantController@store`) — explicitly checks
  `$request->user()->tenantUsers()->where('status', 'active')->pluck('tenant_id')` before
  accepting a `tenant_id`, i.e. it authorizes inline rather than via a Policy class. Confirmed
  correct.

### 3. `inventory/stock/movements` has no top-level nav entry
Not orphaned — it's linked directly from within `inventory/stock/index.tsx` (a "View
movements" link), a deliberate drill-down from the parent screen rather than a first-class
sidebar destination. Listed because the brief asked to flag "reachable routes with no nav
entry" explicitly; recorded as a non-issue after reading the page source.

### 4. Stale docblock in `SeedTenantRolesAction`
The class docblock says "Permissions only cover what actually exists today (tenancy/
identity) ... Extend PERMISSIONS_BY_ROLE as each domain lands" — this predates the S2-S4
domains shipping; the actual `PERMISSIONS` array already covers all 11 domains (catalogue,
purchasing, inventory, equipment, sterilization, labeling, traceability, compliance,
reporting). Purely a stale comment, not a functional issue.

### Checked and clean (explicitly, since these were the other mismatch categories asked for)
- Permissions defined but never checked anywhere: **none.**
- Permissions checked but granted to no role (an always-403 route): **none.**
- Inertia pages with no route, or routes rendering a page that doesn't exist on disk:
  **none** — all 29 unique page paths cross-checked 1:1 against `resources/js/pages/**/*.tsx`.
- Nav items pointing at a 404: **structurally not possible** here — every `href` in
  `navigation.ts` is built from a Wayfinder-generated, typed route helper
  (`resources/js/routes/**`) with a `@see` back-reference to the real controller
  method/line; a renamed or removed backend route fails `tsc --noEmit` (confirmed green) at
  build time rather than 404ing at runtime.
- API routes missing from `docs/openapi.yaml`, or spec paths with no matching route:
  **none** — exact-match set diff, 94 vs 94, zero delta either direction.
- A role reaching a page whose data it shouldn't see: not found. All view/manage permissions
  in this app are practice-wide by design (any role with e.g. `patients.view` sees every
  patient in the tenant, not a role-scoped subset) — that matches CLAUDE.md's product model
  (a small practice team, not per-role data partitions within one tenant), so this isn't
  flagged as a defect; there is no stated design intent it violates.

## Public / authenticated-only API routes (no permission — by design)

Six single-action API controllers sit outside the permission model entirely, correctly:

| Route | Middleware | Why no permission |
|---|---|---|
| `POST /api/v1/auth/login` | `public-api` throttle only | Pre-authentication by definition |
| `POST /api/v1/tenants` (register) | `public-api` throttle only | Self-serve signup, pre-authentication |
| `POST /api/v1/invitations/accept` | `public-api` throttle only | Token-authenticated, not session-authenticated |
| `DELETE /api/v1/auth/logout` | `auth:sanctum` | Any authenticated user logs out their own session |
| `DELETE /api/v1/auth/tokens` (logout-everywhere) | `auth:sanctum` | Same — acts on the caller's own tokens only |
| `GET /api/v1/me` | `auth:sanctum` | Returns the caller's own identity only |
